## Symptom

**[INITIAL INVESTIGATION STATE — superseded by the dated RESOLUTIONs later in this record, which are the current normative answer. Retained under the append-only rule.]** A **commercial ROM boots and executes real code but does not reach video** (Phase 5 capstone). Through the retail HLE boot (`rom::hle_boot`) the game's own IPL3 runs, the CPU fetches the cartridge's instruction stream, and the PC advances through hundreds of millions of retired instructions across varied routines — but no frame is scanned out: over ~10 s of emulated time `VI_CTRL` stays 0, `VI_ORIGIN` is never set, and **no interrupt of any kind fires** (SM64 witnessed at `retired ≈ 9.4×10⁸`, all MI interrupt lines clear)

## Suspected mechanism

The retail OS-boot runtime the game waits on is not yet modeled. A commercial title's boot is interrupt-driven: after its OS initializes, its main loop blocks on the **VI vblank interrupt**, which the emulator only raises once the game programs `VI_CTRL`/`VI_V_INTR` — and the game does not reach that programming, indicating an earlier dependency (the **RI/RDRAM interface** registers used for RDRAM sizing, and/or the OS thread/interrupt setup). This is a cross-subsystem gap spanning the VI vblank loop, the RI registers, and the F3DEX graphics microcode — all **outside the Phase 5 cart/boot/saves boundary** (ADR 0003; the cart phase delivers PI/SI/PIF/CIC + saves, not the OS runtime)

## Classification

absolute — a coverage boundary across subsystems, not a fitted constant or a timing interval

The `CACHE`/I-cache hypothesis is **eliminated**: the fetched words match RDRAM exactly. **ROOT CAUSE FOUND AND REPRODUCED — an interrupt is charged to the `ERET`, not to the instruction it returns to (2026-07-29).** Catching the fatal `EPC` write in the act (cycle-stepping with a pipeline-history ring buffer) gives an unambiguous verdict: `EPC 0xFFFF_FFFF_8001_3678 -> 0xFFFF_FFFF_8003_29A4`, **`EXL 0->1`**, `Cause = 0x0000_0400` (`IP2`, the RCP line), **verdict: EXCEPTION ENTRY**, with the history showing `EX/DC 0x8003_29A4:ERET` -> `DC/WB 0x8003_29A4:ERET` at that exact cycle. The preceding instructions are `LUI k0,0xA430` / `ADDIU k0,k0,12` / `SW k1,0(k0)` — a write to **`MI_INTR_MASK` (`0xA430_000C`)**, i.e. an interrupt handler's epilogue unmasking the RCP and returning. **The mechanism:** `ERET` resolves in **EX** (`ex_stage`), where it clears `Status.EXL` and points `next_pc` at `EPC`. `dc_stage` runs its interrupt check one cycle later; `EXL` now reads 0, so `interrupt_pending()` is true and `abort_from(Stage::Dc, ..)` charges the interrupt to whatever sits in `ex_dc` — **the `ERET` itself**. `EPC` is overwritten with the `ERET`'s own address, the return address it was about to consume is destroyed, and the handler returns to the `ERET`, which resumes at itself. This is the reverse-cascade stage hazard the conventions warn about: an instruction's architectural effect becoming visible to an earlier-running stage one cycle before it retires. **Reproduced in a unit test** — `an_interrupt_across_an_eret_is_charged_to_the_target_not_the_eret` — which yields `EPC == KSEG0_PROG`, the `ERET`'s own address, exactly matching the live signature. **It is `#[ignore]`d because it reproduces an OPEN defect; no fix is shipped.** **Two false starts are recorded because each was caught by a rule rather than by luck.** (a) The first version of the test **passed vacuously**: `dc_stage` re-samples `Cause.IP2` from `bus.poll_irq()` every cycle, so seeding `IP2` on the COP0 block is erased on the next cycle and *no interrupt was ever taken* — the assertions passed on a machine that did nothing. A caveat on scope, stated rather than buried: these five refutations are each *unit* refutations against a synthetic vector, and they do not prove the same paths are configured correctly under a live retail command stream — they prove the paths themselves are bit-exact when driven directly. **THE SILENT COHORT CHARACTERIZED — they HALT, each differently (2026-07-29).** Dumping what actually reaches `WB` at one-cycle granularity, the titles issuing zero RDP commands are not stalled mid-work; they have **deliberately stopped**, the same shape Super Mario 64 had before the PIF fix. **Banjo-Tooie**: `B -1` at `0x8001_36A0` with `Status = 0x0000_FF01` (`IE = 1`, `IM = 0xFF`, `EXL = 0`) and `Cause.IP = 0` — an unconditional self-loop with interrupts enabled and nothing pending, so nothing can ever release it. **Donkey Kong 64**: `BNE v1, v0, -1` at `0x8000_0A04` with **`IE = 0`** (registers given by ABI name, as elsewhere in this row; the raw encoding is `r3`/`r2`, and that they are **`v0`/`v1` — the return-value pair** — is itself a hint: the loop is comparing two returned values, so tracing what last wrote them is the way in) — a spin-poll comparing two registers with interrupts *disabled*, and the delay slot is a `NOP`, so **neither register is reloaded inside the loop**; it is unexitable by construction unless something outside changes them, which with `IE = 0` cannot be an interrupt. That is the most distinctive of the three and the best next target. **Jet Force Gemini**: `B -1` at `0x8003_F5D8` with `IE = 0` **and `Cause.IP = 0x04` (IP2, the RCP line) pending but masked**, while still servicing the occasional exception — its preamble `SD t0, 88(k0)` retires — so it is halted rather than frozen. **`osMemSize` is now doubly weakened as a lead:** seeding `RI_SELECT = 0x14` (the documented IPL3 configuration, `TSEL = 0b0001`, `RSEL = 0b0100`, N64brew *RDRAM Interface* §RI_SELECT) so IPL3 takes the RDRAM-already-up branch changed **nothing** — `osMemSize` stayed `0`, the silent titles stayed silent, and Super Mario 64 was unaffected. Refuted cheaply rather than assumed. **So the remaining work is per-title root-causing, not one shared fix**: each of these reached a halt for its own reason, exactly as SM64 reached its assert because `osContInit` miscounted controllers. The method that worked there is the method to repeat — find the branch into the halt, read what it tested, and trace that value back.

## Donkey Kong 64 — root cause located (2026-07-29)

The first of the 24 silent titles traced to a specific, falsifiable gap, using
the method that worked for Super Mario 64: dump what actually retires, read what
the branch tested, trace the value back.

DK64 reaches an unexitable spin at `0x8000_0A04`. The retired path into it is:

```text
0x800009E0  LUI  a0, 0xA02F
0x800009E4  ORI  a0, a0, 0xE1C0     ; a0 = 0xA02FE1C0  (uncached; physical 0x2FE1C0)
0x800009E8  LW   t6, 0(a0)          ; first read of that word
0x800009EC  LUI  v1, 0xAD17
0x800009F0  ORI  v1, v1, 0x0014     ; v1 = 0xAD170014   <- expected magic
0x800009F4  BEQ  v1, t6, 5          ; match -> 0x80000A0C, continue booting
0x800009F8  LUI  t8, 0xF0F0         ; (delay slot)
0x800009FC  LUI  t7, 0xA030
0x80000A00  LW   v0, -0x1E40(t7)    ; v0 <- [0xA02FE1C0]  -- the SAME address again
0x80000A04  BNE  v1, v0, -1         ; branches to ITSELF -> spin
0x80000A08  NOP                     ; (delay slot)
0x80000A0C  ORI  t8, t8, 0xF0F0     ; the taken-branch path
0x80000A10  JAL  0x80000980
```

The game reads the checked address **twice** — into `t6` at `0x8000_09E8` and
into `v0` at `0x8000_0A00` — and both reads return `0`. The loop is then
unexitable by construction: `BNE v1, v0, -1` branches to **itself**, so the
`LW` at `0x8000_0A00` is *outside* the loop body and `v0` is never reloaded;
`v1` is a constant and the delay slot is a `NOP`.

*(An earlier revision of this record said only that `v0` is zero and never
loaded. That was imprecise: `v0` **is** loaded, once, from the same address — a
reviewer asking for the omitted delay slot and branch target is what surfaced
it. The conclusion is unchanged and slightly strengthened, since the address is
now shown to be read twice with the same result.)*

**Measured, not inferred:**

* `[0x002F_E1C0]` reads **`0x00000000`** on every frame from 1 to 12, and the
  whole surrounding 4 KiB page is **0/4096 non-zero** — nothing ever writes
  there.
* The expected word `0xAD17_0014` occurs in the cartridge image at ROM offset
  **1872 (`0x750`)**, which is inside the **IPL3 bootloader** (ROM `0x40..0x1000`).
* RDRAM is the full 8 MiB, so the address is mapped and in range — this is not
  an Expansion Pak sizing problem.

**So DK64 checks that a word from IPL3 was copied into RDRAM at `0x2FE1C0`, and
in this emulator nothing ever performs that copy.** It is the classic
anti-tamper shape: verify a known boot word survived at a known address, hang if
not. The gap is a missing write, not a wrong value.

**Next step:** find what performs that copy on hardware — the candidates are a
PI DMA the game issues that we do not complete, or a boot-time relocation of the
IPL3 image that `rom::hle_boot` skips along with IPL1/IPL2. Determine which
before writing anything: seeding the word directly would fabricate evidence of a
copy that never happened, which is the failure this ledger exists to prevent.

### Narrowed further: the word exists, at the wrong address (2026-07-29)

Searching RDRAM directly rather than trying to catch a PI transfer in flight
(`PI_WR_LEN` reads back `0` once a transfer completes, so register sampling
cannot see one):

| Check | Result |
| --- | --- |
| `0xAD17_0014` present in RDRAM? | **yes — at `0x0000_0200`** |
| ROM `0x740..0x760` (a slice *within* IPL3) in RDRAM? | **yes — at `0x0000_01F0`** |
| Highest non-zero RDRAM byte | **`0x0010_03FF`** |
| Pages `0x2F0000`, `0x2FE000`, `0x300000` | **0 / 4096 non-zero** |

Two things follow. First, the ROM-to-RDRAM offset is consistent: ROM `0x740` →
RDRAM `0x1F0` and ROM `0x750` → RDRAM `0x200`, a uniform `0x550`. Second, RDRAM
stops at `0x0010_03FF`, which is exactly the **1 MiB the game's initial code payload occupies, plus the
`0x400` load base**. (Naming: IPL3 is the 4 KiB bootloader at ROM `0x40..0x1000`; the
`0x400..0x1003FF` RDRAM region is the payload IPL3 *transfers*, not IPL3 itself.) — so the IPL3 copy itself completed correctly and
nothing else has loaded yet.

**So the expected word is not missing from the machine — it is at `0x200`, and
DK64 reads `0x2FE_1C0`, roughly 3 MiB up, in a region nothing has written.**
That reframes the gap: it is not a failed DMA of *this* word, but a boot or
load step that should have placed a copy of the boot block high in RDRAM before
this check runs, and does not.

The `hle_boot` path skips IPL1/IPL2, so the first candidate was a copy performed
by that skipped sequence. **The comparison was run, and it settles it.**

### ANSWERED: DK64's hang is an artifact of the HLE boot, not an emulation defect

| | `hle_boot` | `real_pif_boot` |
| --- | --- | --- |
| `[0x2FE_1C0]` | `0x0000_0000` | **`0xF0F0_F0F0`** |
| surrounding page | 0 / 4096 | 7 / 4096 |
| highest non-zero RDRAM byte | `0x0010_03FF` | **`0x003C_0B2F`** (~3.9 MiB) |
| PC after 30 frames | `0x8000_0A08` — **the spin** | **`0x8000_0A88` — past it** |

Under the real PIF chain DK64 **clears the check and keeps running**. The
`0xF0F0_F0F0` it leaves there is its own marker, written on the taken-branch
path by the `LUI t8, 0xF0F0` / `ORI t8, t8, 0xF0F0` pair either side of the
branch — so the game reached code that only executes when the check passes.

Over 240 frames the difference is visible end to end: under HLE, DK64 never
programs `VI_CTRL` at all; under the real PIF it reaches `VI_CTRL = 0x0320E`
and scans out a real **625x237** frame with **8,422 lit pixels**. It still
issues no RDP commands, so it is not finished — but it is no longer hung.

**This is title-specific, not a general boot deficiency.** Under the same
comparison Banjo-Tooie, Jet Force Gemini and 1080 Snowboarding are unchanged,
and Super Mario 64 — the control — issues exactly 80,417 RDP commands either
way, so the real-PIF path introduces no regression.

**Methodological consequence, which matters more than the one title:** the
corpus census and every commercial measurement in this ledger run through
`hle_boot`. For at least one title that path produces a hang the hardware boot
does not, so a "silent" verdict from the census is a statement about the *HLE
boot* as much as about the emulator. The census should be re-run under
`real_pif_boot` for the silent cohort before any of those 24 titles is
attributed to an emulation defect.

### The re-census was RUN, and it refutes the concern above (2026-07-29)

The full corpus was censused through **both** boot paths, 420 frames each, same
two-term rule (>= 1,000 RDP commands **and** >= 1,000 lit pixels):

```text
=== 66 titles: HLE renders 29, real-PIF renders 29 ===
GAINED under real-PIF (0):
LOST under real-PIF (0):
real-PIF boot setup failed (0):
```

**The boot path makes no difference to the render count, and the rendering set
is identical.** So the "24 silent titles" figure is **not** an artifact of
`hle_boot`, and the warning in the preceding paragraph — that the figure was "a
count under the HLE boot path, not a count of emulation defects" — was
**overstated**. It is retained above as written, per the append-only rule,
because the reasoning that produced it was sound and only the conclusion was
wrong: DK64 *is* boot-path-sensitive, and generalizing from one title to the
corpus was the error.

**What the two paths actually differ on:**

| | HLE | real-PIF |
| --- | --- | --- |
| titles rendering | 29 | **29** |
| titles issuing zero RDP commands | 24 | **25** |
| zero only under one path | — | **World Driver Championship** |

To be explicit about that arithmetic: **the original 24-title silent cohort is
unchanged** — every one of those 24 issues zero RDP commands under *both* paths,
and no title left the cohort. The 25th is **World Driver Championship**, an
*additional* real-PIF-only regression, not a member of the original cohort.

* **Donkey Kong 64 remains boot-path-sensitive but still does not render.** Under
  the real PIF it clears its anti-tamper check, programs `VI_CTRL = 0x0320E` and
  scans out 625x237 with ~13.5k lit pixels — versus never programming the VI at
  all under HLE. But it issues **zero RDP commands either way**, so it fails the
  two-term rule on both paths and the count is unchanged. Lit pixels with no RDP
  work behind them is the Rayman 2 / Namco Museum 64 signature; that frame needs
  the look-at test before anyone calls it progress.
* **World Driver Championship REGRESSES under the real PIF**: 176,085 RDP
  commands to **zero**, `VI_CTRL` `0x13046` -> `0x0311E`. It rendered nothing on
  either path (`lit = 0`), so the headline count is unaffected, but this is a
  real defect in the real-PIF path and the one title where HLE is strictly
  better. **Tracked as its own work item** rather than left as a remark; the
  method is the one that worked for SM64 and DK64 — dump what retires under
  real-PIF, find where it diverges from the HLE run, read what the branch
  tested.
* **Everything else looks like timing noise — stated as an INFERENCE, not a
  measurement.** What is measured is that the remaining deltas are 0.7-1.0 % of
  the command count with *identical* lit-pixel totals (Majora's Mask 231,244 ->
  229,014; Banjo-Kazooie 189,526 -> 187,725). The attribution to extra IPL1/IPL2
  execution shifting the sample points is the *plausible reading* of that, and it
  is consistent with the identical pixel totals, but nothing here isolates the
  cause per title. Establishing it would need a differential trace on one title,
  which has not been run. Recorded this way deliberately: "it is only timing" is
  exactly the kind of dismissal that, taken on faith, hides a real per-title
  divergence inside a small percentage.

**Consequence for the plan:** the 24 remaining silent titles are genuinely
silent under both boot paths, so each really does need its own root-cause hunt —
the shortcut hoped for here does not exist. **ONE OF THE TWO COHORTS RESOLVED — and it was not a boot defect (2026-07-30).** The census's *other* finding, the single title `real_pif_boot` made strictly worse, is now closed: World Driver Championship's real-PIF silence was an **`AI_STATUS.FULL` livelock** (ledger R-16), not anything to do with IPL1/IPL2. It polls bit 31 for a free audio DMA slot *before* programming the DAC, and an unprogrammed `AI_DACRATE` stopped the DAC — while the only place a drained transfer is retired sits inside the DAC's own sample step, so the flag latched permanently. Diagnosed by counting **transitions** rather than sampling the bit (48 under HLE, **exactly 1** under real-PIF), which is this row's own `Cause.ExcCode` lesson applied on purpose rather than relearned. Fixed against ares' structure, not a guess. **Re-censused: real-PIF is now 29 render / 24 zero-command, identical to HLE, so no title is boot-path sensitive in that partition any more.** What it does *not* do is make WDC render: it issues 175,815 commands and lights **zero** pixels, the same clears-and-draws-nothing shape recorded for it under HLE earlier in this row. `docs/STATUS.md`'s figures stand as written.
